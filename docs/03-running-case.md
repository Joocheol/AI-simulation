# 03 · 러닝 케이스 사양 — 뱅크런

## 1. 케이스 서사

### 1.1 가상 은행 설정

> **K저축은행 중앙지점** (가상)
>
> 지역 기반 저축은행. 총 예수금 **800억 원**, 예금자 **2,000명**. 대면 창구 4개와 모바일 앱을 운영합니다.
> 어느 월요일 아침, 이 은행의 부동산 PF 대출 부실 소문이 지역 커뮤니티와 메신저를 타고 퍼지기 시작합니다.

모든 수치는 **가상**입니다. 스케일은 공개된 실제 사례에서 빌렸으나 특정 금융기관을 지칭하지 않습니다.

### 1.2 모델이 답해야 할 질문

| # | 질문 | 답하는 모델 |
|---|---|---|
| Q1 | 위기 당일 인출액은 얼마나 나올까? | M1 |
| Q2 | 유동성이 바닥날 확률은 몇 %인가? | M2 |
| Q3 | 창구가 그 인출을 감당할 수 있나? | M3 |
| Q4 | 불안은 어떻게 번지고 언제 폭발하나? | M4 |
| Q5 | **무엇을 하면 막을 수 있나?** | M5 |

### 1.3 중심 통찰

**SVB(앱 채널)는 하루 만에 끝났고, 새마을금고(대면 창구)는 한 달에 걸쳐 진행됐습니다.** 같은 뱅크런의 전개 속도를 가른 것은 채널 구성과 처리용량입니다.

이 대비는 M3(채널)과 M4(확산)를 결합했을 때 수강생이 스스로 발견하게 됩니다 — **창구 처리용량을 늘리면 대기줄은 짧아지지만 유동성은 더 빨리 소진됩니다.** 직관을 배반하는 이 결과가 실습5 토론의 핵심입니다.

## 2. 모델 시간 축 — 트랙 A / B

### 2.1 제약의 실체

PLE는 **1회 실행당 모델시간 5시간**을 제한하되 **Process Modeling Library 사용 모델은 예외**입니다. 이를 모델별로 대조하면:

| 모델 | PML 사용 | 필요한 모델 시간 | 5시간 제한 위험 |
|---|---|---|---|
| M1 인출액 확률모델 | ✗ | **0~1틱** | 사실상 없음 |
| M2 몬테카를로 | ✗ | **복제당 0~1틱** | 사실상 없음 |
| M3 채널 폭주 | **✓** | 1~5일 | 면제 대상(추정) |
| M4 예금자 확산 | **✓** (M3 결합) | 3~7일 | 면제 대상(추정) |
| M5 정책 비교 | **✓** | 3~7일 | 면제 대상(추정) |

> **긴 모델 시간이 필요한 모델은 전부 이미 PML을 쓰고, PML을 안 쓰는 모델은 모델 시간이 거의 필요 없습니다.**
> 즉 이 제약은 설계 구조상 이미 대부분 해소되어 있으며, 남는 것은 **불확실성 자체**입니다 — PML 면제 조건이 "블록이 하나라도 존재하면"인지 "실제로 개체가 통과해야"인지 확정되지 않았습니다.

**몬테카를로는 "모델시간 1,000틱"이 아니라 "복제 1,000회"** 이므로 원칙적으로 제한과 무관합니다. 다만 제한이 **복제 합산으로 계산될 가능성**이 남아 있고, 그렇다면 M2가 통째로 막힙니다 → [07 · 검증 T4](07-ple-verification.md) 필수.

### 2.2 트랙 A (권장) — 검증 T2 통과 시

| 항목 | 값 |
|---|---|
| 시간 단위 | **분 (MINUTE)** |
| 총 모델 시간 | 7일 = 10,080분 |
| 영업시간 | 09:00–16:00 (Schedule 블록으로 표현) |
| 추상화 | **없음** |

서비스 시간 7분은 "7분", 소문 잠복 6시간은 "360분", 7일 실행은 "10,080분". **학습자가 단위 때문에 헷갈릴 일이 0입니다.** M1·M2는 정지시간을 1틱으로 두어 "하루치를 한 번 뽑는 모델"로 설계하므로 제한과 무관합니다.

### 2.3 트랙 B (폴백) — T2 실패 시

| 항목 | 값 |
|---|---|
| 시간 단위 | **초 (SECOND)** |
| 규약 | **1틱 = 현실 1분** |
| 예산 | 5 모델시간 = 18,000틱 = **현실 12.5일** (여유 충분) |

환산: 1시간 = 60틱 / 1영업일(7시간) = 420틱 / 1일 = 1,440틱 / 1주 = 10,080틱

#### 트랙 B의 필수 완화책

추상 시간 단위는 개념이 어려워서가 아니라 **운영 규율이 무너지는 순간** 혼란스러워집니다. AnyLogic을 처음 보는 사람에게 모델 시간 단위에 대한 사전 기대 자체가 없기 때문입니다. 실패 지점은 다음 네 가지이며, 각각 대응이 필요합니다.

| 실패 지점 | 대응 |
|---|---|
| 차트 축·시계가 "초"인데 강사는 "일"이라 말함 → 엑셀 능숙자는 단위에 민감하므로 미세한 불신이 쌓임 | 모든 차트 x축을 `time()/1440`로 그려 **"경과 일수"로 사전 라벨링** |
| **PML 블록의 개별 단위 드롭다운이 규약을 조용히 깨뜨림** — Delay/Service의 지연시간 필드는 자체 단위 선택기가 있어, "2"를 넣고 드롭다운을 `minutes`로 두면 120틱 = 규약상 현실 2시간이 됨. **원인 파악이 거의 불가능** | 모든 블록 단위 드롭다운을 **초로 사전 고정**, 워크북에 *"드롭다운은 절대 건드리지 않기"* 명시 |
| 분포 파라미터 해석이 계속 틱 기준 | 워크북 **모든 페이지 상단에 환산표 고정 배치** |
| *"실제 은행엔 어떻게 적용하죠?"* → *"무료판 제약 때문입니다"* 라고 답하는 순간 도구와 과정의 신뢰도가 함께 하락 | 프레이밍 전환 (아래) |

**프레이밍 전환:** 강사 대본에서 **"초"라는 단어를 금지**하고 항상 **"틱"** 이라 부릅니다. 그리고 정당화를 바꿉니다.

> ~~"무료판 제약이라서 이렇게 합니다"~~
> → **"시뮬레이션에서는 시간을 무차원 단위(틱)로 두고 해석하는 것이 표준적인 좋은 습관입니다"**

이는 OR·물리 모델링의 실제 일반 관행이므로 사실에 어긋나지 않으며, 학습자에게 오히려 한 단계 높은 개념을 줍니다.

### 2.4 채택하지 않은 안 — "영업시간 창(window)" 모델링

*위기 당일 09:00–14:00 = 5 모델시간으로 잘라 PLE 한도에 맞추는 안.*

| 사유 | 설명 |
|---|---|
| **자체 모순** | 은행 영업시간 9–16시는 **7시간**이라 5시간 창과 맞지 않습니다. "영업시간을 그대로 모델링한다"는 이 안의 유일한 장점이 시작부터 성립하지 않고, 10–15시만 자르면 *"왜 3시에 문을 닫죠?"* 라는 질문이 나옵니다 |
| **서사 훼손** | 소문 확산·야간 여론 증폭·익일 개점 시 대기행렬은 하루 안에 담기지 않습니다. 특히 **정책 P3(즉시 커뮤니케이션)의 효과는 다일 지평 없이는 보여줄 수 없습니다** |
| **불필요** | 2.1에서 보듯 긴 모델시간이 필요한 모델은 이미 PML 면제 대상입니다 |

> **다만 서사 소재로는 채택합니다.** SVB식 디지털 뱅크런은 실제로 시간 단위로 진행되므로, **오프닝 사례와 실습3(채널 폭주, 하루 지평)** 에서는 이 관점을 그대로 씁니다.

## 3. 시나리오 파라미터

모두 **가상 수치**이며, 학습자가 조정하는 값은 ⚙ 로 표시했습니다.

### 3.0 ⚠ 단위 규약 — 모든 rate는 환산해서 넣습니다

문서에는 읽기 쉬운 **"일 단위"** 로 적되, 모델에는 **모델 시간 단위로 환산한 값**을 넣습니다. **이 환산을 빠뜨리면 1,440배 오차가 나고 오류 메시지는 뜨지 않습니다.**

| 문서 표기 | 트랙 A (분) | 트랙 B (1틱 = 1분) | 분모 |
|---|---|---|---|
| 창구 도착 200건/일 | 200 ÷ 420 = **0.476건/분** | 동일 | **420** (영업 7시간) |
| 창구 도착 400건/일 | 400 ÷ 420 = **0.952건/분** | 동일 | 420 |
| 확산계수 β = 0.6/일 | 0.6 ÷ 1440 = **0.000417/분** | 동일 | **1440** (24시간) |
| 결심 지연 평균 0.5일 | **720분** | 720틱 | 1440 |

> **분모가 두 종류입니다.** 창구 도착은 영업시간(420분) 중에만 발생하므로 420으로, 확산은 밤에도 진행되므로 1,440으로 나눕니다. 혼동하기 쉬우니 모델 제작 시 반드시 구분하십시오.
>
> **환산은 템플릿에 사전 반영합니다.** 학습자는 "일 단위" 값을 슬라이더로 조작하고 내부 변환은 모델이 처리하므로, 학습자가 환산을 직접 할 일은 없습니다.

### 3.1 창구

| 파라미터 | 값 | 비고 |
|---|---|---|
| 창구 수 `c` | **4** ⚙ | 정책 P1의 의사결정 변수 |
| 처리시간 | **`triangular(4, 6, 11)` 분** | 평균 **7.0분** |
| 영업시간 | 09:00–16:00 = **420분** | Schedule로 표현 |
| **창구 처리용량** | **240건/일** | 4 × 420 ÷ 7 |
| **평시 창구 도착** | **200건/일** | 인출뿐 아니라 입금·이체·상담 등 일반 업무 포함 |
| 평시 이용률 | **83.3%** | 평균 대기 **6.9분** |
| 포기(reneging) | 대기 60분 초과 시 이탈 | 이탈자의 50%는 앱으로 전환 |

> **평시 이용률 83%는 의도적입니다.** "여유 있어 보이는 상태에서 조금만 늘어도 무너진다"가 이 과정의 핵심 체험이고, 오프닝 퀴즈의 수치([08 · 오프닝](08-instructor-runbook.md#00000010--오프닝))가 정확히 이 설정에서 나옵니다.

### 3.2 예금자 — M4 확산 대상

| 파라미터 | 값 | 비고 |
|---|---|---|
| 예금자 수 `N` | **2,000명** | 실제 3만 명 규모의 축소. PLE 한도·랩톱 성능 모두 여유 |
| **초기 불안 예금자** | **20명 (1%)** | ⚠ **확산의 씨앗.** 이것이 없으면 모델이 영원히 아무 일도 하지 않습니다 (3.4 참조) |
| 총 예수금 | 800억 원 | 1인당 평균 4,000만 원 |
| 초기 가용 유동성 `L0` | **120억 원** ⚙ | 총 예수금의 15% |
| 1인당 인출액 | **`triangular(50, 800, 5000)` 만 원** | 최소 50 / 최빈 800 / 최대 5,000만 원 |
| 인출 채널 선택 | 창구 50% / 앱 50% ⚙ | 위기 시 채널 구성을 바꿔 볼 수 있는 변수 |

> **인출액에 로그정규 대신 삼각분포를 씁니다.** ① `lognormal()`의 인자 순서가 미확인 상태이고([07 · A8](07-ple-verification.md#3-함께-확인할-항목)), ② 삼각분포는 인자 순서 실수가 용서되며, ③ 실무자가 "최소·보통·최대"로 직접 추정할 수 있어 교육적으로도 낫기 때문입니다. 실제 업무 적용 시에는 데이터로 분포를 적합하는 것이 맞습니다.

### 3.3 앱 채널

| 파라미터 | 값 | 비고 |
|---|---|---|
| 처리시간 | 1분 | 사실상 즉시 |
| 동시 처리 용량 | 500 | 물리적 대기줄 없음 — **SVB형 채널** |
| 1일 인출한도 | **무제한** ⚙ | 정책 P2에서 **1인당 500만 원**으로 제한 |

### 3.4 확산 동학 (M4)

| 파라미터 | 값 | 비고 |
|---|---|---|
| 확산계수 `β` | **0.6 /일** ⚙ | 위기강도: 중 `0.4` / 고 `0.8` |
| 결심 지연 | `exponential`, 평균 **0.5일** | 불안 → 인출시도 |
| 전이식 | **`beta * 불안비율()`** | 학습자가 입력하는 유일한 표현식 |

> ⚠ **초기 시드가 반드시 필요합니다.** 전원이 `평온`에서 출발하면 `불안비율()`이 0이므로 `beta * 불안비율()`도 0이고, **전이가 영원히 일어나지 않아 확산 곡선도 인출도 발생하지 않습니다.** CP7 달성이 불가능해집니다.
> 따라서 `M4_start`에는 **불안 상태 예금자 20명(1%)이 미리 배치**되어 있습니다. 강사는 이것을 *"소문은 20명에게서 시작합니다"* 라고 설명하면 됩니다.
>
> *심화 대안(선택):* 시드 대신 1일차에만 작동하는 미디어 충격 상수항을 더해 `mediaShock(t) + beta * 불안비율()` 로 둘 수도 있습니다. 초보자에게는 시드 쪽이 이해하기 쉬워 기본안으로 채택했습니다.

## 4. 모델 진화 스펙 (M1 → M5)

### M1 · 위기 당일 인출액 확률모델 — 실습1

| 항목 | 내용 |
|---|---|
| **추가 요소** | 파라미터 3개(`N`, 인출 참여율, 위기배수), 분포식 1개, 이벤트 1개, 히스토그램 1개 |
| **새 개념** | 확률변수, 분포 선택, 난수와 **시드(재현성)** |
| **사용 분포** | `triangular(50, 800, 5000)` — 치트시트에서 권장하는 기본 선택 |
| **모델 시간** | 1틱 (하루치를 한 번 뽑음) → 모델시간 제한과 무관 |
| **출력** | 당일 총 인출액 분포 |
| **완성 판정 (CP2)** | 실행 버튼을 눌렀을 때 히스토그램에 막대가 그려진다 |
| **핵심 순간** | *"시드를 바꾸면 결과가 달라집니다. 그럼 어느 게 맞나요?"* → M2로 연결 |

### M2 · 몬테카를로 — 실습2

| 항목 | 내용 |
|---|---|
| **추가 요소** | **사전 제작된** Monte Carlo 실험 + Output 객체. 학습자는 **복제 횟수만 변경** |
| **새 개념** | 복제, 수렴, 신뢰구간, **꼬리위험** |
| **모델 시간** | 복제당 1틱 |
| **출력** | 인출액 분포 히스토그램, **P(인출액 > L0)**, 95% 신뢰구간 |
| **완성 판정 (CP4)** | 1,000회 복제 후 **유동성 부족 확률과 신뢰구간을 워크시트에 기록** |
| **핵심 순간** | **"평균으로 보면 안전한데, 5% 확률로 파산합니다."** |

> ⚠ **학습자가 Monte Carlo 실험을 직접 만들게 하지 마십시오.** Output/Dataset 설정은 초보자에게 30분짜리 벽이며, 이 세션의 학습 목표가 아닙니다. 상세는 [02 · 2.1](02-schedule.md#21-실습2에-대한-중요한-설계-결정).

### M3 · 채널 폭주 — 실습3

| 항목 | 내용 |
|---|---|
| **추가 요소** | `Source → Queue → Service → Sink` + `ResourcePool`(창구직원 4). 대기열 길이·대기시간 차트 |
| **새 개념** | 이산사건, 개체(entity), 자원, 대기행렬, 포기율 |
| **모델 시간** | 1~5일 (PML 사용 → 면제 대상) |
| **도착률 설정** | 평시 **200건/일** → 위기 **400건/일** (학습자가 바꾸는 숫자 하나) |
| **출력** | 대기열 길이 추이, 평균·95% 대기시간, 포기 건수 |
| **완성 판정 (CP6)** | 위기 도착률에서 **대기열이 발산하는 것을 육안으로 확인** |

**왜 400건인가 — 검산**

| 도착 | 평시 대비 | 이용률 | 평균 대기 |
|---:|---:|---:|---|
| 200건/일 | 1.00배 | 83.3% | 6.9분 |
| 228건/일 | 1.14배 | 95.0% | 31.2분 |
| 300건/일 | 1.50배 | **125%** | **발산** |
| **400건/일** | **2.00배** | **167%** | **발산 (명백)** |

> 오프닝 퀴즈는 **228건(미묘한 지점)** 으로 직관을 깨고, 실습3은 **400건(명백한 붕괴)** 으로 눈에 보이게 합니다. 용량 240건/일을 넘는 순간 대기열은 정상상태에 도달하지 못하고 영업 종료까지 계속 늘어납니다.
> 2배는 과장이 아닙니다 — 새마을금고 2023년 7월 중도해지 건수가 전년 동월의 2배였습니다.

### M4 · 예금자 확산 — 실습4

| 항목 | 내용 |
|---|---|
| **추가 요소** | 예금자 Statechart — **상태 4개** `평온 → 불안 → 인출시도 → 완료`, **전이 3개** |
| **사전 제공** | 에이전트 타입, population, **초기 불안 20명 시드**, **결합부**, 헬퍼 함수 `불안비율()` |
| **새 개념** | 에이전트, 상태도, 전이 트리거, 확산 동학 |
| **모델 시간** | 3~7일 |
| **출력** | 상태별 인원 추이(S자 곡선), 누적 인출액, 유동성 잔액 |
| **완성 판정 (CP7)** | β를 0.3 → 0.9로 바꿨을 때 확산 곡선의 기울기가 변하는 것을 확인 |

**상태와 전이**

| # | 전이 | 트리거 | 식 |
|---|---|---|---|
| 1 | 평온 → 불안 | Rate | **`beta * 불안비율()`** ← 학습자가 입력 |
| 2 | 불안 → 인출시도 | Rate | `1 / 결심지연` (사전 설정) |
| 3 | 인출시도 → 완료 | Message | 인출 처리 완료 시 (사전 설정) |

> `완료` 상태가 있어야 **같은 예금자가 반복해서 인출하지 않습니다.** 학습자는 상태 4개와 전이 3개를 그리고, 그중 **전이 1의 식 한 줄만** 입력합니다.

#### ⚠ 에이전트–프로세스 결합 방식 (설계상 가장 중요한 결정)

Statechart에서 프로세스 흐름으로 개체를 넘기는 방법은 세 가지이고, 초보자 부담이 크게 다릅니다.

| 방식 | 필요한 코드 | 초보자 적합성 |
|---|---|---|
| ① `Enter` 블록 + 전이 액션 `main.enterWithdrawal.take(this)` | Java 1줄 + 에이전트 타입 일치 | **부적합** — `this`, 점 표기법, 타입 개념이 **동시에** 등장 |
| ② `Source.inject()` 호출 | Java 1줄 | 부적합 (정도는 덜함) |
| ③ **Source 도착률을 상태별 인원수의 함수로 연결** | **학습자 코드 0** | **✅ 채택** |

③을 채택합니다. **"불안한 예금자가 많아질수록 창구 도착률이 올라간다"** 는 서사가 개념적으로도 더 올바르고(개체를 하나씩 넘겨야 하는 상황이 아닙니다), 학습자가 조작하는 것은 **결합계수 숫자 하나**뿐입니다. 이 계수를 슬라이더로 노출해 두면 *"결합 강도를 올리면 어떻게 되나?"* 라는 실험까지 자연스럽게 이어집니다.

**소문 확산도 같은 원칙으로** — 메시지 전파(`send("rumor", ...)`)는 코드입니다. 대신 전이 트리거를 `Rate`로 두고 `rate = beta * 불안비율()` 형태의 **평균장(mean-field) 감염 구조**를 씁니다. `불안비율()`은 템플릿에 사전 제작하고, 학습자는 드롭다운에서 트리거 유형을 고른 뒤 `beta * 불안비율()`을 **따라 입력**합니다. 엑셀 수식 입력과 체감상 동일하고, SIR 전염병 모델과 같은 구조라 설명도 직관적입니다.

### M5 · 정책 비교 — 실습5

| 항목 | 내용 |
|---|---|
| **추가 요소** | 정책 스위치 3개 + **시나리오당 20복제 실험(사전 제작)** + 비교 워크시트 |
| **새 개념** | 시나리오 실험, 트레이드오프, 정책 권고 |
| **실행** | 정책 3안 + 기준 × 위기강도 = **6개 시나리오**, 각 **20복제** |
| **완성 판정 (CP8)** | 비교표를 채우고 **권고안 1줄을 적는다** |

> ⚠ **시나리오당 1회 실행으로는 확률을 말할 수 없습니다.** 단일 실행은 유동성 소진 여부가 0 또는 1로만 나오고, 난수 시드에 따라 정책 순위가 뒤집힐 수 있습니다.
> 따라서 각 시나리오를 **20복제로 사전 구성**하고, 학습자는 정책 스위치를 바꿔 **6번 "실행"** 합니다. 한 번의 실행이 20복제를 돌려 **P(유동성 소진)** 을 내놓습니다.
> 학습자 부담은 버튼 누르기로 동일하면서, **실습2에서 배운 복제 개념이 여기서 실제로 쓰입니다.**
>
> 📌 **20복제 × 6시나리오의 실행 시간을 [파일럿](04-labs-and-materials.md#4-제작-일정)에서 반드시 실측하십시오.** 25분 슬롯에 들어오지 않으면 복제를 10회로 줄이고, 그래도 안 되면 위기강도를 "고" 하나로 좁혀 4시나리오로 축소합니다.

#### 정책 대안

| # | 정책 | 구체적 설정 | 기대 효과 | 숨은 비용 |
|---|---|---|---|---|
| **기준** | 무조치 | 창구 4, 한도 없음, β 그대로 | — | — |
| **P1** | 창구 증원 | `c`: 4 → **8** | 대기시간 급감, 포기율 감소 | **유동성이 더 빨리 소진됨** |
| **P2** | 인출한도 | 앱 1일 한도 **1인당 500만 원** | 유동성 소진 지연 | 불안 증폭 가능 (β 상승) |
| **P3** | 즉시 커뮤니케이션 | 위기 인지 후 **β × 0.5** | **확산 자체를 억제** | 실행 가능성·신뢰도 리스크 |

**위기강도:** 중 `β = 0.4` / 고 `β = 0.8`

> **토론 유도 포인트:** P1은 고객 경험(대기시간)을 개선하지만 유동성 소진을 **앞당깁니다.** 빨리 처리할수록 돈이 빨리 나가기 때문입니다. "좋은 서비스"가 위기를 악화시킬 수 있다는 결과는 거의 모든 수강생의 직관을 배반하며, 이 과정에서 가장 오래 기억되는 장면이 됩니다.
